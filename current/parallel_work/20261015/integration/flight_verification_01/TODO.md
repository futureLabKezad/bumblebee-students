# Измерения для полной полётной приёмки

Текущее средство подготовлено, но не заморожено для нового combined. Preflight revision09 завершился отказом без ARM и без PARAM_SET; ожидается исправленный кандидат revision10. Ожидаемые SHA нельзя обновлять по результату неуспешного полёта. После отдельного ревью combined и окончательной заморозки flight tools основной агент создаёт новый снимок через `freeze_pins.py`.

## S1: начало координат и первый взлёт

До первого переданного setpoint нужно сохранить доказательство преобразования координат. Подходят закреплённый исходник используемой версии PX4/GZBridge с описанием преобразования либо инструментированная пара стартовых NED и Gazebo GT, записанная до цели. Для пары требуются обе временные отметки, позиции, определения кадров и независимо зафиксированная матрица вращения. По одной паре нельзя одновременно подбирать перенос и вращение. Оценку EKF следует отделить от истинной координаты; её начальная неопределённость не исчезает из отчёта.

Из этих данных формируется `origin-evidence.json`: NED-координаты ENU-ноля, метод, источник вращения, исходные пары, временное совмещение и SHA доказательств. Подбор origin после просмотра первой цели запрещён. Если исходник задаёт обычное ENU↔NED, преобразование имеет вид `(E−E0, N−N0, D0−D)`; иной поворот требует явной поддержки в verifier, а не применения этой формулы по умолчанию.

Затем нужны первый действительно переданный PX4 position packet, GT до и после него с общей шкалой времени, один SET_MODE OFFBOARD, один ACCEPTED ARM и полный журнал STATUSTEXT/PX4 без «No offboard signal». Verifier должен добавить полную required-check таблицу S1, сохранив отдельно сравнение с оценкой EKF. Физическая ошибка первой цели должна быть менее 5 см. Отсутствующие origin или данные команды оставляют конкретное условие unknown; наличие всех доказательств должно позволить завершить S1.

## S5: передача управления пилоту

Нужно сохранить внешний SET_MODE POSCTL на проводе, первый настоящий source1/1 POSCTL heartbeat, переход PX4 ULog в POSCTL и ответ SDK на последующий navigate. Во всём интервале до отдельного cleanup необходим полный proxy с обоими типами целей и проверенные часы PX4/Gazebo.

Измеряются последняя цель относительно фактического перехода POSCTL и относительно первого POSCTL heartbeat. Текущие численные условия: не более 1,1 секунды симуляции от перехода до последней цели и отсутствие целей позже 0,1 секунды после heartbeat. Дополнительно проверяются отказ SDK и отсутствие вооружённого возврата OFFBOARD по ULog, а не только редким heartbeat. Команды cleanup ограничивают конец наблюдения и не входят в отказ SDK. При наличии этих данных текущие дополнительные условия S5 можно включить в полную таблицу приёмки; постоянная заглушка unknown для S5 не требуется.

## S8: посадка и следующий взлёт

Нужен один SITL-сеанс с двумя отдельными полётными циклами. После первой посадки следует сохранить касание и DISARM, фактическое событие возврата safe_land=True, состояние OFFBOARD disarmed и полный независимый возврат 19 значений, включая устойчивое чтение. Первый journal и все чтения нужно сохранить отдельно до подготовки второго поколения транзакции: новая prepare может заменить текущий journal.

Только после этого допускаются новая prepare, применение профиля и разрешение второго взлёта. Успех подтверждается новым фактическим ARM и физическим подъёмом по GT, а не ответом navigate. После второго полёта снова требуются DISARM и возврат 19 значений. В отчёте нужны массивы `cycles[0]` и `cycles[1]` с собственными журналами, SHA и временными границами. Текущие одиночные before/after/stable не заменяют доказательство первого восстановления между циклами.

Скорость снижения измеряется по истинной скорости ULog: окно после начала LAND и до касания, число точек, медиана, квантили, минимум и максимум. Ожидаемое значение около 0,4 м/с выводится рядом. Численный допуск нельзя выбирать после просмотра результата. Для автоматического PASS нужен отдельно рассмотренный критерий до запуска; без него сохраняются измерения и отдельная оценка этого качественного условия. Касание и DISARM измеряются независимо: ожидаемый интервал около 2 секунд, действующий численный предел verifier составляет 3 секунды. Добавление второго взлёта и полной таблицы S8 выполняется после появления артефактов.

## S9: общая шкала времени heartbeat

Допустим отдельный явно объявленный вариант только для SITL: `sys_status.conn_timeout=120` настенных секунд у фактического plugin MAVROS. Сначала по ROS-графу определяется узел plugin; затем сохраняются исходное значение и реальное чтение применённых 120 секунд. Родительское `conn.timeout` не является доказательством. Настройка находится в отдельном YAML запуска; общие конфигурации, физика и таймауты PX4 не меняются. Область приёмки должна прямо содержать эту временную настройку приёмника.

Каждая фаза начинается сразу после зарегистрированного свежего переданного heartbeat source1/1. Сохраняются его PX4 time_boot_ms, wall-время, момент включения подавления и фактический интервал. Нельзя считать 3,5 секунды от произвольного proxy_clock равными возрасту последнего принятого heartbeat. Прокси подавляет только настоящий FCU HEARTBEAT; позы, остальные сообщения и частоты потоков не подменяются.

Короткая фаза 3,5 секунды симуляции должна сохранить поток, armed OFFBOARD и отсутствие дополнительных ARM/MODE. После подтверждённого свежего heartbeat выполняется длинная фаза 5 секунд. Проверяются остановка целей C++ по watchdog 4,5 секунды от принятого State, fallback PX4 после потери целей и отсутствие возобновления управления после восстановления heartbeat до DISARM. Фактические wall-интервалы и восстановление должны уложиться в 120 секунд; если таймаут MAVROS всё же сработал, изоляция C++ не доказана.

После этого verifier получает отдельную полную таблицу S9 с проверкой применённого sim-only параметра и измеренных фаз. Результат прежней модели с реальными часами остаётся дополнительным свидетельством. Его нельзя переносить на полёт с PX4/Gazebo.

## Общие условия

Для каждого нового запуска сохраняются raw gate, независимый core и итог проверки профиля. Общий PASS требует `success_before_cleanup`, независимых before/after/stable всех 19, restored journal без pending, закреплённых исходников и полного набора условий выбранного сценария. Успешный cleanup после отказа не меняет полётный результат. Неизмеренные условия перечисляются поимённо с необходимым следующим действием; они не удаляются из таблицы приёмки.
