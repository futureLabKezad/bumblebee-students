**Не менялись:**

### Почему Б2 тоже (обоснование выбора)
- Б1 убирает закрытия шлюза из-за мигания. Но у пола детектор не видит метку подолгу.
  - В первых 15 с после взвода (s10, 40 прогонов) промежуток «SEARCHING → NORMAL» + 8 пустых кадров: медиана 0,83 с, p90 1,5 с, максимум 2,1 с.
  - 58 из 152 промежутков длиннее 0,9 с (`/work/t42_takeoff_ev_resets_20261110/out/gate_log.jsonl`).
- Это дольше, чем 0,5 с (срок свежести позы в vpe_fix) + 0,4 с (EKF бросает зрение). Значит, и с Б1 паузы и сбросы у пола останутся (скорее всего). Они будут короче: дрейф и смена смещения меньше.
- Остаётся шум одного кадра. Его и убирает Б2.
- Ожидание: сбросов больше 0,10 м станет мало или не будет (возможно). Проверит только прогон.

### Часы сторожа (W) — выбор: ROS clock при use_sim_time, иначе monotonic
- Это те же часы, что держат удержание simple_offboard и `_hold_now()` в drone.py. В SITL сторож меряет секунды симуляции, на дроне (нет use_sim_time) — monotonic.
- С monotonic в SITL при RTF 0,85–0,9 срок 6,0 с настенных часов = 5,1–5,4 с симуляции. Сторож сработал бы раньше, чем на дроне, и С8 выглядел бы лучше, чем есть.
- Оценщик С8 меряет время по журналу PX4, то есть по времени симуляции. Часы симуляции дают в SITL то же поведение, что на дроне (доказано по коду `_hold_now`, тест `WClock`).
- Защиты:
  - ROS clock = 0 (ещё нет /clock) считается monotonic;
  - если вид часов сменился между меткой и «сейчас» — monotonic;
  - отрицательный возраст (часы пошли назад, перезапуск Gazebo) = +inf: сторож срабатывает, посадка;
  - момент события по-прежнему `time.monotonic()` (`_vpe_pose_time`, `_vision_arm_t`). Метка часов удержания снята тем же замером и используется, только если совпадает с этим моментом. Иначе — monotonic, ровно как r2g.

### Пункт 3 поручения (T41) — не включён
- Причина T41 не в образе. HTE PX4 включается только после dist_bottom > 1,0 м, а flight_marker летит на 0,7 м (доказано, `/work/t41_marker_landing_20261110`).
- Правка была бы в высоте полёта скрипта или стенда либо в настройках PX4. Это отдельное решение.

Что показывают новые тесты (доказано на коде):
- **Мигание метки** 0,4 с есть / 0,3 с нет:
  - r2h — ни одной паузы публикации > 0,4 с за 20 с;
  - r2g — паузы ≥ 0,9 с.
- **Метки вернулись** — r2h открывает шлюз на этом кадре (+3 кадра Б2), r2g ждёт такта 1 Гц.
- **Метки пропали** — шлюз закрывается через 1,5 + 0,5 с, как раньше. Поза старше 0,5 с не уходит никогда.
- **Без захвата курса, взведён не в OFFBOARD, FCU неизвестен / нет State 4,5 с** — шлюз закрыт, даже если метки идут.
- **После паузы 1 с:**
  - r2h молчит до 3-й свежей позы, затем 0,5 с шлёт медоиду (выброс +0,05 м не уходит), потом последнюю позу;
  - r2g шлёт первую позу сразу и выброс следом.
  - Без паузы и при разрыве < 0,3 с Б2 не включается.
- **Сторож** (fly_to, takeoff, поток поз, обрывающийся в любой фазе цикла):
  - r2h — посадка через срок + ≤ 0,1 с;
  - r2g — до + 0,5 с.

**Не проверено здесь** (чего тесты не покажут):
- ROS-тесты и gtest не запускал (поручение: без ROS).
- Как Б1/Б2 меняют полёт в Gazebo — покажут прогоны Симулятора.
- Install пересобран colcon. Исходники C++ те же, что в r2g (`diff -rq src`: отличаются только 2 файла Python). Бинарники побайтно с r2g не сравнить: путь папки другой длины, а он вшит в бинарники. `vpe_fix.py` в install = src (cmp).
- Известное ограничение Б2 (возможно): после принудительного перезасева в vpe_fix (`_maybe_reseed`) в медоиду могут попасть позы до перезасева, если им < 0,5 с. Перезасев идёт, пока поток не прерывается, поэтому паузы и Б2 там обычно нет.
