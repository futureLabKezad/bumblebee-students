## С5 — как считается
- **Высота скрипта H** берётся из кода скрипта прогона (единственный вызов `drone.takeoff(height=…)`), а не из ключа запуска. SHA256 файла сверяется с `versions.txt` прогона: не совпала — FAIL.
  - flight.py r2: 0,8. Старый port_03: 1,5.
- **Окно:** от первой точки во взведённом состоянии, где |h − H| ≤ 0,10, до команды посадки (выход из OFFBOARD) или выключения моторов. Каждая точка окна по Gazebo — в полосе ±0,10: проверяется **наибольшее** отклонение.
  - Время смены режима в журнале точное: vehicle_status пишется сразу при смене; в s04 21,548 с = nav_state_timestamp (доказано).
- **Касание:** первая точка после окна, где высота по Gazebo ≤ 0,01 м над полом и скорость вниз < 0,1 м/с. В Gazebo модель на полу стоит ровно на h = 0 (s04), поэтому 1 см — это касание.
- **Выключение:** первая запись vehicle_status после касания, где arming_state ≠ ARMED. Задержка должна быть ≤ 3,0 с.
- **Ни одного аварийного режима** — за весь прогон. Провал, если есть хоть что-то из списка:
  - флаг failsafe или failsafe_and_user_took_over;
  - nav_state AUTO_RTL, DESCEND или TERMINATION;
  - «Kill engaged»;
  - код выхода скрипта ≠ 0 или неизвестен.

## С7 — как считается
- **Маршрут — из кода скрипта** (SHA256 сверяется с `versions.txt`): вызовы `drone.fly_to(x=, y=)` по порядку — числа или цикл `for (a, b) in СПИСОК`. Другие формы — FAIL «не понят».
  - Маршруты r2 совпали с критерием (доказано тестом): flight_marker — (0; 1,4) → (0; 0,7) → (0; 0); flight_marker_loop — 0→1→2→3→(7)→13→12→11→(5)→1→0.
- **Сделанные вызовы** — строки `=== FLY TO (…) ===` в script.log. Они должны совпасть с маршрутом из кода: меньше — прерывание.
- **Точки в системе Gazebo:** истинное положение переводится в карту меток по world.sdf и map.txt. Оценка дрона для этого не используется.
- **Момент перехода к следующей команде** — по уставке PX4 (trajectory_setpoint в журнале).
  - Участки, где уставка стоит: меньше 3 мм за отсчёт, не короче 0,4 с; соседние ближе 0,05 м склеиваются (повторный hover).
  - Участок 0 — взлёт, участки 1…N — точки маршрута.
  - Число участков должно быть N, длина каждого перелёта между ними — совпасть с маршрутом в пределах 0,05 м. Иначе FAIL: отрезки не сопоставить надёжно.
- **Ошибка точки:** наибольшее горизонтальное расстояние по Gazebo до точки маршрута — от прибытия до конца участка.
  - Прибытие — когда оценка дрона впервые ближе допуска fly_to (это проверка самого скрипта).
  - Конец участка — когда уставка двинулась дальше, то есть скрипт перешёл к следующей команде.
  - Так покрыты оба случая толкования: «в момент перехода» и «за всё ожидание». В зачёт идёт большее, нужно ≤ 0,25 м. Высота печатается отдельно.
- **Посадка:** горизонтальное расстояние от центра метки 0 до места, где дрон стоит после выключения моторов (среднее за 1 с). Нужно ≤ 0,15 м.
- **Прерывание** — любое из списка:
  - негодный прогон;
  - код выхода ≠ 0;
  - failsafe, AUTO_RTL/DESCEND/TERMINATION или kill;
  - любой режим, кроме OFFBOARD, между взлётом и AUTO.LAND (вмешательство);
  - не достигнутая точка.
- **Счёт подряд:** `c7_eval.py --series OUT_DIR ПРОГОН…` (в порядке полётов).
  - Считается отдельно для каждого скрипта: провал обнуляет счёт.
  - Смена кода или настроек начинает счёт заново с этого прогона. Сравниваются versions.txt без строки даты и SHA256 params_sitl.json.
  - Готово, когда у обоих скриптов 10 подряд.

## Что решил сам — на сверку чату 1
1. Касание: h ≤ 0,01 м и скорость вниз < 0,1 м/с. В Gazebo пол — ровно h = 0. Если взять порог больше, касание будет раньше и проверка строже; разница — доли секунды.
2. Аварийные режимы nav_state: AUTO_RTL, DESCEND, TERMINATION. AUTO.LAND после /land — обычная посадка. В С7 любой другой режим до AUTO.LAND — вмешательство.
3. Скрипт, который закрыл стенд (F4, код 137 или 143), — это «аварийный код выхода», FAIL. С исправлением F4 в r2 скрипт должен закрываться сам.
4. Участки С7 сопоставляются только при точном совпадении числа и длин перелётов (±0,05 м). Иначе FAIL «not evaluated» — честный отказ вместо догадки.
