**F1. Детектор меток «спит» до взвода, а flight.py проверяет метки до взвода.**
- В Gazebo flight.py из-за этого не взлетел («need >=1 markers, got 0») — доказано. На дроне, скорее всего, будет так же.
- а) Детектор включён всегда: одна строка в настройке запуска.
  - Минус: по комментарию в коде детектор занимает около 2 ядер Pi из 4 и принимает весь поток камеры 24 кадра/с всё время, даже на земле. Раньше из-за этого подвисали телеметрия и панель (`aruco_detect.py`:191–199). Не измерено.
- б) Скрипт «будит» детектор только на время проверки, до 15 с: новый сигнал «проснись» от скрипта (заготовка, 2 файла).
  - Плюс: нагрузка только на время проверки.
  - Минус: меняется программа детектора, нужна пересборка образа.
- в) Не проверять метки до взвода, а проверять в воздухе: нет меток — посадка.
  - Минус: дрон взлетает, не убедившись, что видит метки.

**F2. Скрипт «загружает» карту меток, но работающий детектор её не перечитывает.**
- По коду: детектор читает карту один раз при старте, а узел, который скрипт перезапускает, в образе выключен.
- Сейчас вреда нет: карты обоих скриптов совпадают с картой образа по всем 20 меткам, смещение 0 см (доказано).
- Риск: если кто-то поменяет карту в скрипте, дрон молча полетит по старой.
- а) Оставить как есть.
- б) Скрипт только сверяет карту и не летит, если она другая; ничего не пишет и не перезапускает (заготовка).
- в) Научить детектор перечитывать карту — новый код в детекторе, правка больше.

**F4. flight.py не закрывается сам после посадки.**
- Причина (по коду и опыту на Python, доказано): программа ждёт свой рабочий поток, а команда закрыть его стоит в очереди после этого ожидания.
- Опасности нет: моторы к этому времени уже выключены.
- а) Одна правка в общей библиотеке: закрывать поток до ожидания (заготовка). Минус: используется внутренняя функция Python (она есть с версии 3.9, на Pi стоит 3.12).
- б) В конце каждого примера явно закрывать программу. Минус: скрипты учеников всё равно будут висеть.
- в) Оставить: после посадки закрывать Ctrl+C.
